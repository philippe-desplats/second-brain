# Atlas Rules

## When to use atlas/

This is the zone for **maps, indexes, and referenceable entities**. It is the workspace's meta layer, the one that lets you navigate by idea rather than by folder.

## Structure

- `atlas/people/{slug}.md`, people files (contacts, decision-makers, prospects, individual partners)
- `atlas/services/{slug}.md`, your offerings (web-audit, managed-hosting, strategy-consulting, etc.)
- `atlas/topics/{slug}.md`, cross-cutting subjects (ai-agents, kubernetes, seo, accessibility, supply-chain-security)
- `atlas/maps/{slug}.md`, thematic MOCs and generated static indexes, distinguished by `subtype: moc | index`, plus `atlas/maps/{slug}.base` for live Bases views
- `atlas/home.md`, main hub, the workspace's single entry point

## Types and schemas

| File | BM type | BM schema | Validation |
|---|---|---|---|
| `atlas/people/*.md` | `person` | `basic-memory/schemas/person.md` | strict |
| `atlas/services/*.md` | `service` | `basic-memory/schemas/service.md` | strict |
| `atlas/topics/*.md` | `topic` | `basic-memory/schemas/topic.md` | strict |
| `atlas/maps/*.md` | `note` + `subtype: moc \| index` | `basic-memory/schemas/note.md` | warn |
| `atlas/home.md` | `note` + `subtype: moc` | same | warn |

## MOC (Maps of Content)

Manual thematic maps for dense subjects that deserve an entry page. For the template, see `templates/atlas-moc-template.md`.

Naming convention, `MOC-{subject}.md` or `{subject}-moc.md`:

- `atlas/maps/MOC-ai-agents.md`
- `atlas/maps/MOC-kubernetes.md`
- `atlas/maps/MOC-workspace-methodology.md`

## Indexes

Indexes exist in two forms, and the split is deliberate: a `.base` file is a query and never goes stale, a `-static.md` file is a snapshot and does.

**Live views**, shipped as `.base` files. Bases is an Obsidian core plugin, so these work in a fresh clone with nothing to install. Obsidian 1.10 or later is required, since `atlas/home.md` uses a `list` view:

- `atlas/maps/clients-active.base`, clients with `status: active`
- `atlas/maps/partners-active.base`, partners with `status: active`
- `atlas/maps/projects-active.base`, project briefs with `status: active`
- `atlas/maps/recent-emails.base`, the most recent emails, plus a view listing sent mail, which knows nothing about whether a reply came back

**Static snapshots**, generated by `python3 basic-memory/scripts/generate_indexes.py`, readable outside Obsidian by any editor and by agents. Run it after a significant writing session, or weekly. The script writes `clients-active-static.md`, `partners-active-static.md` (only when `sources/partners/` exists), `projects-active-static.md`, `recent-emails-static.md` and `decisions-recent-static.md`.

**Never label a Bases column with `file.name`, and check what a folder filter actually catches.** Entity context files are all named `CLAUDE.md` and project briefs are all `README.md`, so such a column reads "CLAUDE" or "README" on every row. Use the note's identity property: `client`, `partner`, `title`, or `subject` depending on the type, and add `file.folder` when location matters. The exception is a view over files whose names are already unique and descriptive, such as the MOC list.

A folder filter also catches that folder's own `README.md`. A view over `knowledge/` must filter on what makes a note distilled knowledge, its `subtype`, not on its location alone. Both defects were shipped once and only surfaced when the view was rendered, never by validation.

**One index is static only.** `decisions-recent` reads `- [decision]` observations from note bodies. Bases filters on properties, not on body content, so there is no `.base` equivalent and there never will be without a different mechanism. Do not add one.

**Portability**, a `.base` file renders only inside Obsidian; outside it, it is an inert YAML file rather than dead query text in the middle of a note. The `-static.md` versions carry the equivalent lookups in plain markdown. They are not always identical: `recent-emails.base` shows the most recent messages while its static twin cuts at fourteen days, because a Bases filter cannot express a rolling window without a date formula. Leaving Obsidian means regenerating the statics, and the `.base` files can simply be deleted.

## MOC frontmatter

```yaml
---
title: MOC, {Subject}
type: note
schema_version: 1
subtype: moc
date: YYYY-MM-DD
status: active
topics: [topic1, topic2]
---
```

## Static index frontmatter

Emitted verbatim by `generate_indexes.py`. A `.base` file has no frontmatter at all; it is pure YAML configuration.

```yaml
---
title: {Index name}
type: note
schema_version: 1
subtype: index
date: YYYY-MM-DD
generated: YYYY-MM-DD
auto_generated: true
---
```

`date` is the note's own date, required by the `note` schema. `generated` is the freshness marker `/sb-doctor` reads to flag an index older than seven days.

## Wiki-link conventions

MOCs contain **dense** wiki-links to:

- Modeled entities (`[[Person]]`, `[[Service]]`, `[[Topic]]`)
- Clients or partners involved (`[[Globex]]`, `[[Initech]]`)
- Active projects (`[[Globex Website Audit]]`)
- Distilled knowledge (`[[playbook-client-onboarding]]`)
- External sources (URLs)

The goal is for a MOC to act as a visual aggregation node in the Obsidian graph.

## Obsidian color groups

To make the graph more readable, configure color groups:

- `type:client-context` -> green
- `type:partner-context` -> dark green
- `type:meeting` -> blue
- `type:email` -> gray
- `type:person|service|topic` -> orange
- `type:note` + `subtype:pattern|playbook|guide` -> red
- `type:project-brief` -> purple
- `type:note` + `subtype:moc|index` -> black/outline

## Maintenance

- MOCs are not created by default; they emerge when a subject becomes recurring and deserves an entry point.
- MOCs decay over time; run an annual review to archive the ones no longer in use.
- Bases views refresh automatically when opened in Obsidian. Static indexes need the generation script.

## Forbidden rules

- No raw artifact (email, transcript, meeting notes) in `atlas/`
- No wikilink in the `name:` or `title:` frontmatter (unless the value is deliberately text)
- No MOC without relations in its body (a MOC with no links aggregates nothing)
